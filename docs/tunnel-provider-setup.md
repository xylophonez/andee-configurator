# Tunnel provider setup pack

This pack covers the **provider** side of an AndEE tunnel. Put the public tunnel service on a measured LapEE or other reviewed PermawebOS host. The AndEE phone is the client: it connects out to the provider. The August LapEE pilot proved the transport and signed location publication on physical hardware. Payment to an independent operator remains dependent on Sam's reviewed charging and settlement configuration.

## Choose the route

If your router accepts inbound connections, forward public TCP 443 to the measured provider and terminate TLS there. If the site is behind CGNAT or filtered inbound, use an always-on LAN companion to initiate a connection to a public relay/VPS and forward it to the provider. The companion carries packets; it does not become the measured node. LapEE itself has no shell or WireGuard service for holding the outbound relay leg.

You need a dedicated LapEE-capable machine with TPM 2.0 and Secure Boot provisioned, a domain you control, DNS automation for a wildcard TLS certificate, a public endpoint, and reviewed device implementation pins. Keep operator signing material and any AR/AO funds under the operator's control. Use an isolated test node and disposable identity for the first run.

The adjacent [`tunnel-provider-basic.json`](./tunnel-provider-basic.json) is a **transport and discovery template**, not a paid provider profile. It pins the tunnel device used in the August pilot and starts `location@1.0` publication. Replace its URL and review its pin and signer against the actual provider build before applying it. It contains no payment hook or fee promise. Do not publish it as a paid service.

The template's one-hour `location-ttl` and boot-only publication are suitable for a short pilot. A continuously listed provider needs a renewal job or hook that republishes with a newer nonce before the TTL expires. Set the TTL in milliseconds for the reviewed HyperBEAM build, and test the renewal and Arweave indexing delay. A live tunnel registration does not publish its provider location record automatically.

## Apply and check

1. Build and boot the reviewed LapEE image on the provider hardware. The detailed image, USB, Secure Boot and network procedures are in the existing physical pilot `PROVIDER-GUIDE.md` in `lapee-baseline-sam-20260721`; preserve that staged worktree. Check the TPM quote and measured boot before exposing the service.
2. Put the public HTTPS URL in `location-url`, and set DNS/TLS and the direct or companion route. Read back the operator config from the boot medium. The LapEE init rejects an entire invalid operator config; avoid reserved keys such as `measurement-body-source`.
3. Boot the provider. Check its public `~tunnel@1.0/status`, scalar tunnel pin under `~meta@1.0/info`, node address, `~meta@1.0/info/on/request`, and `~measurement@1.0` evidence. A live status response alone is not measured admission. HyperBEAM may show the request hook as `1+link`; read `/~meta@1.0/info/on/request/1` to see the actual `{device: "tunnel@1.0", path: "request"}` handler. A client-side tunnel pool or connect hook is not provider evidence.
4. Publish the signed location record with the `POST`, `target: self`, `commit-request: true` start hook after configuring the public `location-url`, codec, bundler endpoint and TTL. Check the returned record's signer, URL, nonce, TTL and Arweave item, then query the location registry after indexing. The pilot location item is `9Be-civMMQJsXt85aS28zZey3cHqCWOwQm9-v36vudA`. In the HyperBEAM source, even `GET /~location@1.0/node` can generate and asynchronously upload a record; do not use it as a read-only health check. Without `location-url`, that call may advertise a localhost default.
5. Use a disposable AndEE client to register and send a synthetic request through the public HTTPS address. Check both request and response, the client's public URL, and the provider's registration count. For the Mystical-style wildcard route, the client hostname starts with the lowercase base32 encoding of the 32 address bytes; it is not the 43-character base64url node address. Decode the client address, base32-encode those bytes, and append `.tunnel.mystical.computer`. A request to `/~meta@1.0/info/address` through that hostname must return the client address, not the broker address. Then test provider restart, client reconnect and stale-location behavior.
6. Before charging anyone, substitute a reviewed paid-provider config with the exact tunnel, metering, ledger and P4 pins, enforced price/terms, payment recipient, and settlement flow. The existing pilot paid-broker example has four unresolved implementation placeholders and token-gated quota; it is **not** an operator payout profile.

For rollback, restore the previous operator config and public edge route, restart the provider, and publish a fresh location record for the restored URL. If a key or device pin changes, force clients to refresh their configuration. Arweave's earlier location records remain visible; a newer signed nonce and expiry are how crawlers move on.

## What to hand to the market

Supply the node signer, public HTTPS URL, signed location item, measurement evidence, reviewed tunnel implementation pin, operational status, and enforced price/terms. The market must verify those facts independently before displaying the provider as eligible. The present browser finder can discover and probe candidates but cannot make that admission decision yet.

## Why `tunnel.mystical.computer` is absent today

Read-only checks on 29 September 2026 found a working public router at `https://tunnel.mystical.computer`: `~tunnel@1.0/status` reported one registration, no client pool, and `/~meta@1.0/info/on/request/1` exposed the tunnel request handler. The router's node address is `0riQX0qXO8qQb0T4utpdr39SYUfs5LdCh-rWdj6qtk4`. Its current VPS config has no `location-url`, `location-ttl`, `location-codec`, `bundler-ans104`, or location publication start hook. Arweave GraphQL returned no location record for that node address under either supported tag schema, and no record with the exact Mystical URL. The browser finder therefore has no candidate to discover. An earlier finder revision also missed this router because the hook was linkified; the local finder now resolves numbered hook entries safely.

To list the current broker as an **unverified candidate**, review its config and publication path, add `https://tunnel.mystical.computer` as the explicit location URL, arrange authorized signed publication and renewal, and confirm the resulting Arweave record is indexed with the broker's signer and URL. Recheck the candidate in the finder after publication; its five-page/60-probe browser crawl can still omit an older record and says when coverage is incomplete. This is an operational change to a live broker and an Arweave upload, so prepare and review it before applying it.

The VPS currently returns HTTP 500 with `device-name-not-resolvable` for `~measurement@1.0`. It is a plain, unmeasured relay/router. Publishing its location would not make it a measured PermawebOS provider. For that admission standard, run the trust-bearing tunnel node on measured LapEE or another reviewed PermawebOS machine and use the VPS only as the public network leg, or keep the VPS explicitly marked as a curated unverified starter route until a different policy is agreed.

A 29 September Pixel 9 sidecar check exercised the manual Configurator route without publishing a location item. The browser generated a 418-byte `next.json` for `https://tunnel.mystical.computer` with the live tunnel pin. AndEE imported it through **LOAD CONFIG**, restarted, and reported the exact file digest. The broker showed eight workers registered under the sidecar's address. The correct base32 child hostname returned the sidecar's node identity and operator digest over TLS. The debug sidecar's measurement policy was rejected as expected, so this proves transport and the operator-config path, not measured-provider admission.
